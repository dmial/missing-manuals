Артефакты-приложения — живые страницы
Где живёт артефактна серверах Anthropic — или на твоём устройстве Серверы Anthropic. Пока не опубликован — часть переписки: живёт внутри диалога claude.ai и отдельного существования не имеет Твоё устройство. Единственный из трёх, кто лежит локально — в хранилище приложения Claude Desktop: галерея Artifacts в сайдбаре, история версий со сравнением и откатом. На другое устройство не переезжает; облачная сессия правит его тоже через приложение Серверы Anthropic — плюс исходник у тебя. Страница-копия хранится на инфраструктуре Anthropic (зритель грузит её с песочничного домена *.claudeusercontent.com), а исходник остаётся обычным файлом .html/.md в проекте — на диске или в облачной сессии
Публикациячто этим словом названо — и в какую зону оно выводит: под аккаунтом или без

«Опубликовать» здесь и значит «сделать публичным».

АвторизованнаяДо Publish артефакт — часть переписки и виден только тебе. Publish вынимает его в раздел Artifacts в сайдбаре: теперь он живёт вне исходного диалога. На Team/Enterprise вместо публичности есть Share — доступ членам организации, каждый под своим аккаунтом
НеавторизованнаяСюда Publish и целится на Free/Pro/Max: ссылку открывает кто угодно, аккаунт Claude не нужен. Публикация — это ещё и выключатель для данных: облачное хранилище (window.storage) работает только у опубликованного артефакта. Пока не опубликован — сохранить он не может ничего, запись просто не проходит. Снимешь публикацию — все накопленные данные удалятся безвозвратно

Публикации нет как действия — есть только версии.

АвторизованнаяЗдесь всё и происходит: артефакт существует с момента создания, лежит на устройстве под твоим аккаунтом в приложении, каждое изменение просто добавляет версию в историю (сравнение, откат). Публиковать нечего — он и так есть
Неавторизованная · пустоЗоны не существует. Отдать страницу человеку без аккаунта нельзя ни одним способом: публичной ссылки у Cowork-артефакта не бывает вообще

«Опубликовать» ≠ «открыть всем»: публикация приватна.

АвторизованнаяСюда попадает всё по умолчанию. Publish — явное действие с подтверждением («Claude wants to publish … to a private page on claude.ai»): страница ложится на серверы Anthropic по приватному URL и видна только тебе, пока не поделишься. Повторная публикация — тот же URL и новая версия, в шапке выбираешь, какую версию видят зрители; чтобы править из другой сессии, надо дать Claude этот URL. Доступ выдают конкретным людям или организации — они входят под своими аккаунтами. Коннекторы живут только в этой зоне: вызов идёт от имени зрителя, значит зритель обязан быть
НеавторизованнаяОтдельный шаг поверх публикации — External sharing: ссылка открывается кем угодно без входа в claude.ai (на Pro/Max это единственный способ поделиться; на Team/Enterprise Owner должен включить). Цена перехода — живые данные: звать коннектор не от чьего имени, поэтому страница с коннекторами в эту зону не попадает ни на одном плане
Вызовы MCP из артефактакто здесь MCP-хост, тот и исполняет вызовы Инфраструктура Anthropic: из браузерной песочницы наружу один выход — api.anthropic.com, поэтому запрос к MCP-серверу физически уходит с серверов Anthropic, а браузер зрителя самих серверов не касается никогда. Каким полем это выражено в теле запроса — не документировано: по роли это ровно то, что делает mcp_servers (адрес держит сторона Anthropic), но утверждать, что используется именно публичное поле API, оснований нет Само приложение Claude Desktop: локальные файлы и stdio-серверы оно читает напрямую — без модели и расхода токенов; коннекторы — те, что одобрены артефакту при создании/обновлении, при открытии страница перезапрашивает свежие данные (маршрутизация remote-коннекторов не документирована; по архитектуре MCP соединение держит хост-приложение). Обновление артефакта из облачной сессии сбрасывает выданные права. «Живой» страница бывает только в разделе Artifacts: там Cowork внедряет в неё мост window.cowork, через который и идут все вызовы6. Превью файла в чате и «Open in Google Chrome» показывают тот же HTML без моста — статичная страница без доступа к коннекторам; так задумано из соображений безопасности claude.ai на стороне зрителя. Различать надо два момента жизни страницы. Пока Claude её собирает, он работает инструментами твоей сессии — в том числе локальными MCP-серверами из .mcp.json: они дают данные, которые запекаются в HTML намертво. Когда страницу открывают, сессии давно нет, страница крутится в чужом браузере — и до серверов на твоей машине ей не дотянуться. Живыми остаются только коннекторы claude.ai: при публикации Claude декларирует список, вне списка страница не позовёт ничего. И каждый вызов идёт через аккаунт того, кто смотрит: claude.ai спрашивает у зрителя разрешение, дёргает коннектор от его имени, возвращает результат — кредов страница не видит вообще, а двое зрителей увидят разные данные по своим правам (у кого коннектора нет, увидит страницу без живых секций). Отсюда же и потолок шаринга: анонимный зритель по публичной ссылке не залогинен — аккаунта, через который делать вызов, просто нет, поэтому страница с коннекторами публичной не бывает ни на одном плане
Персистентность данныхгде живёт состояние мини-приложения Единственный режим с настоящим хранилищем: window.storage — облачное KV Anthropic со скоупами personal/shared; работает только после Publish, unpublish стирает безвозвратно (разрез ниже) Своего хранилища нет: состояние — сам HTML (обновление = новая версия) плюс перезапрос данных из сервисов при каждом открытии Своего хранилища нет: страница статична, «no backend» — форма ничего не сохранит; свежесть — только перезапросом через коннекторы
Что видит зрительправа и роли того, кто открыл страницу Все открывшие видят одну страницу, но не одни данные: shared-скоуп хранилища общий для всех, personal — у каждого свой Самый закрытый режим: делиться можно только внутри организации и только на Team/Enterprise. Зритель тянет данные через свой доступ, не через твой Роли: «зритель» видит те версии, что ты открыл, «редактор» (Team/Enterprise) публикует новые — из своей сессии, по URL страницы. Данные каждый видит свои: коннектор дёргается от его имени, у кого связи нет — увидит страницу без живых секций

5 Где вообще «живёт» агент. Агентский цикл — программа, которая передаёт модели контекст, исполняет её tool-вызовы и возвращает результаты, — есть во всех трёх режимах: Chat с его поиском и исполнением кода — такой же агент. Модель при этом всегда снаружи, на инференс-серверах: у неё ни файлов, ни шелла — только текст на входе и выходе. Различие режимов — где стоит цикл и на каком расстоянии от него инструменты. В Cowork и Code цикл — процесс внутри среды сессии (в локальном Code — прямо на твоей машине), и ядро инструментов работает на нулевом расстоянии: Bash — дочерний процесс цикла, Write — запись на собственный диск; среда — не подрядчик, а окружающий мир, который между вызовами просто продолжает существовать вокруг со всем состоянием. В Chat цикл крутится в бэкенде claude.ai вне какой-либо рабочей среды, и все инструменты до единого — вызовы других сервисов: поиск — сервис, исполнение кода — сервис, выдающий контейнер. В API этот водораздел документирован буквально: client tools — исполняет сторона цикла (Bash, text_editor), server tools — исполняет инфраструктура Anthropic (web search, web fetch, code execution); подробно — в разрезе «одна задача, два исполнителя» ниже. Наблюдаемая проверка: в Chat контейнер может истечь посреди диалога — и диалог продолжится с новым; в Cowork умерла среда — кончилась сессия, потому что сессия и есть жизнь цикла в его среде.

6 Мост window.cowork — что это. JS-объект, который приложение Claude Desktop внедряет в страницу артефакта при открытии в разделе Artifacts (в документации не описан; наблюдение из практической проверки). Схема та же, что у window.storage chat-артефактов (разрез ниже): не стандартный браузерный API, а SDK-мостик платформы. Страница сама не имеет ни сети, ни кредов — всё живое (локальные файлы, данные коннекторов) она просит у моста, вызов исполняет приложение-хост своими правами и возвращает странице только результат. Технологически это старый паттерн «хост внедряет объект в embedded-страницу»: window.external в IE, addJavascriptInterface в Android, window.webkit.messageHandlers в iOS WKWebView. Claude Desktop — Electron-приложение (проверяется листингом бандла: в /Applications/Claude.app лежит Electron Framework.framework), и мост почти наверняка собран штатным механизмом Electron — preload-скрипт плюс contextBridge.exposeInMainWorld(), вызовы уходят по IPC в главный процесс приложения (вывод из стандартной практики Electron, не из кода Anthropic). Самописная здесь только API-поверхность — набор методов и их контракт; транспорт и паттерн устоявшиеся. Не путать с мостом подключённой папки Mac (разрез про git): тот — канал между облачной песочницей Cowork и локальной машиной (копирование файлов, листинг, команды в локальной VM). Технологии у двух мостов разные: локальный IPC между процессами одного компьютера — против сетевого RPC между облаком и Mac плюс локальная VM для исполнения команд. Общий только паттерн брокера: недоверенная сторона шлёт запросы по узкому авторизованному каналу, доверенная исполняет своими правами и возвращает результат.

Скилл, созданный агентом в сессии, — просто папка со SKILL.md: чтобы пережить сессию, он должен попасть в один из каналов выше.

Разрез: client tools и server tools — одна задача, два исполнителя

Термины и цитаты — из документации Messages API. Это фундамент под остальными разрезами: четыре git-контура ниже — частный случай этого деления.

Определение документированное и короткое. Client tools «run in your application» — их исполняет та сторона, что крутит агентский цикл: bash, text_editor, любые собственные тулы. Server tools «run on Anthropic's infrastructure» — их исполняет сама Anthropic: web_search, web_fetch, code_execution.

Различие видно не в том, что тул делает, а в том, прерывается ли ход. Клиентский вызов останавливает генерацию: API возвращает stop_reason: "tool_use" — мяч у вызывающей стороны, исполни и пришли tool_result вторым запросом. Серверный не останавливает ничего: Anthropic исполняет тул сама, результат приходит в том же ответе, и вызывающая сторона может вообще не заметить, что был вызов.

Практический смысл деления в том, что инструмент берёт личность у той стороны, которая его исполняет: её сеть, её файлы, её креды, её IP, её права. Поэтому одну и ту же задачу два пути решают по-разному — и равнозначными они не бывают почти никогда.

Что значит «объявлен в запросе к API»

У модели нет никаких «подключений». Каждая её реплика — это один HTTP-запрос к Anthropic с JSON-телом, и всё, что модель знает об инструментах, лежит в этом теле списком. Ничего постоянного за этим не стоит: соседний запрос без нужного поля про инструмент не знает вовсе. И два разных поля тела дают два разных способа выдать тул:

POST /v1/messages
{
  "model": "claude-opus-5",
  "messages": [ ... ],

  "tools": [                        // клиентские: «эти я исполню сам»
    { "name": "run_tests", "input_schema": { ... } }
  ],

  "mcp_servers": [                  // серверные: «сходи туда сама»
    { "type": "url",
      "url": "https://mcp.example.com/sse",
      "name": "example-mcp",
      "authorization_token": "..." }
  ]
}

tools — список обещаний: перечислив тул здесь, вызывающая сторона обязуется исполнить его сама. Модель вызвала — ход остановился, дальше её работа.

mcp_servers — адрес и ключ от чужой двери. Дальше вызывающая сторона не делает ничего: инфраструктура Anthropic сама открывает HTTPS-соединение к указанному URL, спрашивает у сервера список его тулов, вызывает нужный и кладёт в тот же ответ блоки mcp_tool_use и mcp_tool_result. Токен она просто форвардит как Bearer — добыть и обновлять его обязан ты сам.

Вот это и есть «объявлен в запросе»: сервер никуда не установлен и ни к чему не привязан — он назван строкой в теле конкретного запроса. Отсюда и жёсткая граница: поле type принимает единственное значение "url", а сам URL обязан начинаться с https://. Локальные stdio-серверы этим путём не подключаются в принципе — Anthropic просто некуда идти, процесс живёт на твоей машине. Поэтому сервер, который запускается процессом рядом с тобой или смотрит в localhost и интранет, существует только на клиентской стороне: соединение к нему держит тот, кто крутит цикл рядом с ним, — десктоп-приложение (Chat и Cowork) или сама сессия (.mcp.json в Code).

Свернуть весь разрез можно в одну фразу: client tool или server tool — это вопрос о том, на какой стороне живёт MCP-клиент. MCP-клиент — та сущность, которая открывает соединение, здоровается с сервером и запрашивает у него список инструментов (tools/list). Модель не делает этого никогда и ни в одном режиме — ей приходит готовый список. У remote-сервера клиент стоит на стороне Anthropic. У локального им работает программа рядом с тобой: она поднимает процесс по stdio, сама спрашивает список и кладёт полученные тулы в запрос, который отправляет модели.

Отсюда лакмус, для которого не нужно лезть в конфиг: работает ли инструмент с телефона. Документация делит коннекторы ровно по этой линии — remote «available everywhere — web, mobile, Cowork, Desktop, and Claude Code», локальные desktop extensions «only available in Claude Desktop and Claude Code — not on web or mobile». Причина физическая, а не продуктовая: телефон до процесса на твоём маке не дотянется. Значит: видно с телефона — клиент у Anthropic; видно только в Desktop и Code — клиент на твоей машине.

Оговорка к первой строке: имя говорит, кто тул объявил, но не говорит, кто исполняет его дальше. В чистом API web_search — server tool; здесь WebSearch объявлен клиентом сессии, а делегирует ли он внутри себя серверному тулу — изнутри сессии не наблюдаемо. Наблюдаемо только объявление.

Как модель делает выбор

Короткий ответ: между «клиентским» и «серверным» она не выбирает, потому что этого различия не видит. Модель получает один плоский список — имя, описание, схема входа; к какой стороне тул прикреплён, в списке не написано. Это решено до неё, тем, кто собрал запрос: разработчиками режима, а в Code и Cowork ещё и твоим конфигом. Выбор модели — только внутри того, что ей положили.

Выбирает она по совпадению задачи с описанием. Документация формулирует буквально: при tool_choice: auto «Claude determines on each turn whether to call a tool or respond directly. It calls a tool when the request maps to that tool's described capability and the answer isn't already in context». То есть описание тула и есть интерфейс выбора: плохо описанный тул выбирается неправильно, и чинится это текстом описания, а не кодом.

Рычагов управления два. Жёсткий — параметр tool_choice: auto (по умолчанию), any (обязана вызвать хоть что-то), tool (вызвать именно этот), none (нельзя ничего). Мягкий — системный промпт; документация прямо советует фразу вроде «Use the tools to investigate before responding», когда модель ленится вызывать.

Поэтому когда открыты обе двери — как с curl и web_fetch, — выбирает не архитектура, а формулировки. В этой самой сессии выбор навязан промптом: в инструкциях написано брать веб-контент только через WebFetch и WebSearch и не ходить за ним curl'ом; без этой строчки я мог бы пойти любым путём. А сама механика деления включается уже после выбора и без участия модели: клиентский вызов останавливает ход и передаёт мяч вызывающей стороне, серверный исполняется на месте. Модель об этом не думает — это делает API.

Разрез: Git и GitHub — четыре контура доступа

Проверено экспериментально 17.07.2026 на приватном репозитории. Поведение платформы может меняться — это снимок на сегодня.

Все различия сводятся к одному вопросу: откуда у контура берётся право на git-операции. Четыре контура — четыре разных ответа.

Cowork
Code
Локальнокредо-прокси нет; право на git определяется тем, что среда видит из твоих учётных данных

Вручную и заново в каждой сессии: Device Flow на месте или принесённый токен.

Keychain и ~/.ssh в VM не пробрасываются — git сам по себе падает (could not read Username). Готовый токен, принесённый извне, работает и здесь — как в облаке, только кредо-прокси на пути нет. А без токена авторизоваться можно на месте, через OAuth Device Flow, — на пользовательском уровне это одна минута: агент показывает короткий код, ты вводишь его на github.com/login/device в своём обычном браузере и жмёшь Authorize — всё. «Device» в названии — не про тебя, а про того, кто просит доступ: поток придуман для устройств без браузера (smart TV, приставка, CLI на сервере), и здесь таким устройством выступает сама песочница — VM без браузера, которой некуда принять обычный OAuth-редирект; твой браузер играет роль «другой машины», где доступ подтверждают. (Технически: песочница запрашивает у GitHub пару кодов — POST /login/device/code, публичный client_id GitHub CLI, scope repo, — поллит эндпоинт и после Authorize получает gho_…-токен; возможно это потому, что сетевой allowlist включает github.com целиком, вместе с login-эндпоинтами.)

Два следствия дизайна: полученный токен имеет широкий scope repo — все приватные репо аккаунта (fine-grained этот flow не умеет); и это единственный из четырёх контуров, где настоящий токен оказывается внутри среды. Граница дизайна Anthropic проходит здесь: облако защищено брокером, локальный контур — только сетевым списком.

Ничего не настраиваешь: git работает на твоих ключах с машины.

Прямое окружение: git видит SSH-ключ из ~/.ssh и HTTPS-креды из keychain — ведёт себя ровно как у тебя в терминале. Брокера нет; страховка — пошаговые подтверждения команд.
Облакооба контура обслуживает один кредо-прокси: настоящие ключи хранятся у него и в песочницу не попадают никогда; в окружении — токен-суррогат GH_TOKEN, который прокси подменяет настоящими кредами только для репозиториев, прикреплённых к сессии; эндпоинты выдачи токенов не форвардятся — добыть ключи изнутри (device flow) невозможно даже с согласия пользователя

Штатного пути нет: только принесённый готовый токен (PAT).

Прикрепить репозиторий к сессии нельзя — такого UI нет, это фича Code. Список прикреплённых пуст → любой авторизованный запрос к своему репо: 403 not enabled for this session; настройки GitHub App на это не влияют (installation ≠ session-level access; проверено — «All repositories» не помогает). Проходит: анонимный git с публичными репо; и git-протокол с готовым валидным токеном прокси форвардит как есть — PAT, принесённый извне (хоть прочитанный из смонтированной папки), работает.

Отдельная история — git в подключённой папке Mac. Мост — только канал; поверх него три сервиса: копирование файлов, листинг и удалённое исполнение команд в локальной Linux-VM на Mac с прямым маунтом папок. У этой VM нет выхода в сеть (CONNECT → 403; минимальные привилегии): у облака сеть без файлов, у VM файлы без сети. Поэтому git в папке — только офлайн: status, diff, commit, merge — да; pull/push — нет; обмен коммитами с папкой — только bundle-файлами (рецепт в «Практике»). Удалять файлы мост тоже не умеет (rm → Operation not permitted, вместо удаления — перемещение), так что git-локи вроде .git/index.lock из сессии не вычистить.

Из коробки: выбрал репозиторий при старте сессии — дальше всё работает само.

Репозиторий прикрепляется к сессии при создании — выбором из того, что видит подключённый GitHub-аккаунт; скоуп двухступенчатый: «потолок» — доступ аккаунта, вторая ступень — конкретное репо этой сессии. Для прикреплённого репо прокси подменяет суррогат настоящими кредами → полноценные clone/pull/push. Push ограничен текущей рабочей веткой. Установка GitHub App на репозитории скоуп сессии не задаёт (installation ≠ session-level access) — она нужна только для Auto-fix (вебхуки PR).

Практика: если пользоваться git из песочниц. Это уже рекомендации, а не дизайн Anthropic — выше были факты, здесь выводы из них.

  • Облачная сессия, коммиты нужно доставить на Mac → git bundle create в облаке, файл через мост, на Mac — git fetch файл.bundle + merge (сеть не нужна). Застрявшие git-локи чистить в терминале Mac — мост этого не может.
  • Локальная сессия, разовый pull/push → device flow (~1 минута; поллинг статуса — порциями, потому что одна bash-команда в песочнице живёт ~45 секунд). Токен подставлять через credential-хелпер, не записывая в конфиг и не светя в командной строке (иначе виден в ps): 
    git -c credential.helper='!f() { echo username=x-access-token; echo "password=$(cat /tmp/t)"; }; f' pull
    После операции токен удалить; полный отзыв: GitHub → Settings → Applications → Authorized OAuth Apps → GitHub CLI.
  • Постоянный доступ из любых сессий → fine-grained PAT (один репозиторий, Contents: Read/Write, помнить о сроке действия) в файле рядом с репо: 
    git config credential.helper 'store --file .git/gh-credentials'
    Файл не коммитится и живёт на Mac; читается любой сессией, которой подключена папка, включая облачные через мост — это одновременно удобство (закрывает и облачный кейс) и риск (токен на диске открытым текстом).

Разрез: Chat-артефакт как мини-приложение — хранилище window.storage

Выжимка из практической проверки, июль 2026. Относится к chat-артефактам claude.ai.

У chat-артефактов есть облачное key-value хранилище на серверах Anthropic: данные переживают вкладку и сессию чата и живут вместе с артефактом. Доступ — через window.storage, JS-API, который платформа внедряет в песочницу артефакта. Это не стандартный браузерный API и не публичный REST — снаружи, из curl или другого приложения, до хранилища не дотянуться.

await window.storage.set('key', JSON.stringify(data), shared); // запись
const res = await window.storage.get('key', shared);           // {key, value, shared}
await window.storage.delete('key', shared);
await window.storage.list('prefix:', shared);                  // ключи по префиксу

Модель данных: значения — строки (обычно JSON), до ~5 МБ на ключ и ~20 МБ на артефакт; ключи короче 200 символов, без пробелов, слэшей и кавычек. Два скоупа: shared: false — personal, видит только текущий пользователь; shared: true — общие для всех, кто открыл артефакт. get несуществующего ключа бросает ошибку — вызовы оборачивать в try/catch. Конкурентные записи — last-write-wins, синхронизация между устройствами — поллингом. Это KV, а не SQL: ни запросов, ни джойнов, ни транзакций — «выборку» делает клиентский JS после загрузки значения, поэтому связанные данные кладут одним JSON-объектом под один ключ, а не россыпью ключей.

Жёсткие границы. Работает только у опубликованных артефактов — до Publish записи не проходят, в коде нужен фолбэк на память. Namespace намертво привязан к artifact_id: два артефакта не могут читать одну базу ни при каких условиях — общий стейт «веб + мобайл» делается как два интерфейса внутри одного артефакта. Unpublish безвозвратно удаляет все данные, экспорта нет. localStorage/sessionStorage в артефактах не работают — window.storage их замена. Доступно на платных планах. Сеть из артефакта закрыта CSP: разрешены только cdnjs (библиотеки), api.anthropic.com (AI- и MCP-вызовы) и само хранилище — внешнюю БД типа Supabase из артефакта не позвать.

Зачем так спроектировано. Во-первых, артефакт из одноразового демо становится stateful мини-приложением — трекером, журналом, лидербордом — без внешнего бэкенда и деплоя: Publish разворачивает приложение вместе с данными в один клик. Во-вторых, безопасность по принципу deny by default: артефакт — недоверенный код (написан ИИ, открывается посторонними по ссылке), свободная сеть позволила бы сливать данные посетителей — поэтому песочница режет всё, а платформа открывает несколько контролируемых «калиток»: авторизованных, соскоупленных на конкретный артефакт, залимитированных. Модель как у мини-приложений Telegram/WeChat: не «интернет», а SDK-мостики к сервисам платформы. В-третьих, простая модель владения: база живёт и умирает вместе с артефактом — никаких повисших межартефактных связей.

Вывод для архитектуры: один артефакт = одна база. Несколько клиентов на общие данные — либо несколько интерфейсов внутри одного артефакта (личное — в personal, коллективное — в shared), либо настоящий бэкенд с внешней БД за пределами платформы артефактов.

Зачем песочница — и почему в Cowork она несъёмная

Фундамент: ограничение ущерба. Cowork по природе жуёт недоверенный контент — письма, PDF из интернета, веб-страницы, вложения. В любом документе может сидеть prompt-инъекция («забудь инструкции, сделай X»), и агент со свободным шеллом без стенок превращает одну отравленную PDF-ку в доступ ко всей машине: кейчейн, куки, SSH-ключи, все файлы. Стенки песочницы сужают возможный ущерб до подключённых папок. Это фундамент — всё остальное строится на нём. (Изоляция режет только файловый риск; риск коннекторов — действий во внешних сервисах от твоего имени — режется отдельно: выбором подключений и подтверждениями.)

1 · Предсказуемость

Состав среды известен заранее и одинаков у всех: Ubuntu, LibreOffice, pandoc, python-docx/openpyxl, ffmpeg, шрифты с кириллицей. Скилл xlsx работает у бухгалтера ровно так же, как у разработчика, — не потому что у обоих «правильно настроен компьютер», а потому что среду собрала Anthropic. Класс проблем «у меня не работает» почти исчезает.

2 · Воспроизводимость

Каждая сессия стартует из чистого образа — накопленной грязи и дрейфа состояния не существует. Результат зависит только от входов и объявленных зависимостей, а не от истории конкретной машины. Классическое «works on my machine» умирает по построению: нет «my machine».

3 · Автономность

Раз ущерб ограничен стенками, агента можно отпустить: длинные сессии без подтверждения каждого шага, работа при закрытом ноутбуке, задачи по расписанию. Это продуктовая цель Cowork («дал задачу и ушёл» — для любого пользователя, не только эксперта), и она куплена фундаментом. Code устроен зеркально: полный доступ к реальному окружению — в обмен на пошаговый контроль эксперта, который видит каждый push.

Уточнение причинности. Предсказуемость и воспроизводимость — строго говоря, свойства не изоляции, а заранее собранного образа; песочница даёт их «бесплатно», потому что образ и стенки приходят одним пакетом. А вот автономность без ограничения ущерба невозможна в принципе. Цепочка: containment → автономность; предсказуемость и воспроизводимость — попутные инженерные плоды.

Секрет в недоверенной среде считается скомпрометированным. Отсюда кредо-прокси: настоящие ключи хранит брокер, песочницам выдаются короткоживущие суррогаты, привязанные к паре «сессия → репозиторий». Скоуп двухступенчатый: потолок задаёт доступ подключённого GitHub-аккаунта («что аккаунт вообще видит на GitHub» — установка GitHub App потолком не является), выбор при создании сессии — конкретное репо этой сессии. Агент не контролирует ни одну из ступеней: даже уговорённый инъекцией, он упрётся в прокси. Паттерн индустриальный — credential broker / token exchange (OIDC в CI, AWS STS): встретится ещё не раз.

Песочница как дисциплина: зачем работать так по умолчанию

Локальная машина полна неявного знания: пакеты, когда-то поставленные, переменные, где-то прописанные, токены в кейчейне. Работа «просто работает» — пока не сломается или пока её не нужно передать. Песочница эфемерна и пуста, поэтому она заставляет всё неявное сделать явным: зависимости — в setup-скрипт, MCP-серверы — в .mcp.json, процедуры — в .claude/, секреты — в выданные скоупы, ценные результаты — наружу (в репо, в чат, на диск), потому что среда умрёт вместе с сессией.

Побочный эффект дисциплины: работа перестаёт жить в состоянии конкретного компьютера и начинает жить в декларациях. Её может поднять коллега, новая сессия, агент по расписанию, ты сам через год. Это тот же сдвиг, который индустрия прошла путём «works on my machine» → CI → dev containers → инфраструктура-как-код: среда — это код. Практическое правило: облачная песочница по умолчанию для всего автономного и фонового; локально — когда нужна тесная петля или инструменты твоей машины.
